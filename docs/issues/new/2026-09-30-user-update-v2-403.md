# BUG: user update fails with HTTP 403 REPO_10704

---

## Symptoms

`iics user update` (both `--interactive` and `--from-file`) fails with HTTP 403
before any group or role change is applied:

```text
Error: IICS API error (HTTP 403): <error><code>REPO_10704</code><description>Internal
error. An error occurred while loading the user. Contact Informatica Global Customer
Support.</description><statusCode>403</statusCode></error>
```

---

## Command / Reproduction Steps

Observed on the `dev` profile on 2026-09-30 with a freshly created user
(state `Provisioned`, not yet activated):

```bash
iics user create --interactive          # create iics.cli.test.wizard
cat > upd.json <<'JSON'
{"userName":"iics.cli.test.wizard","firstName":"Test","lastName":"Wizardry","email":"iics-cli-test@example.com"}
JSON
iics user update --from-file upd.json   # fails with 403 REPO_10704
```

---

## Expected Behaviour

The user's last name (and in the interactive run, time zone and roles) are
updated.

---

## Actual Behaviour

`Client.UpdateUser` (`internal/client/users.go`) first sends
`POST /api/v2/user/<id>` (XML, legacy V2 update) using the V3 user ID. That
call fails with 403 `REPO_10704`; the following V3 `addGroups` /
`removeGroups` / `addRoles` / `removeRoles` calls are never reached.

This limitation is already noted in `docs/documentation/user.md` (user update
section), which reports HTTP 400 from the same V2 call in earlier testing. The
error has since changed to 403 `REPO_10704`. The CR-0041 update wizard builds
and reviews the change correctly but cannot apply it until this is fixed.

Not yet determined:

- Whether the failure is specific to users in `Provisioned` state (never
  logged in), or happens for all users.
- Whether the V2 endpoint expects a V2 user ID or requires fields the request
  does not send.

## Fix Instructions

1. Check the V2 user update docs (`platform-rest-api-version-2-resources/user`)
   for the ID format and required fields, and compare with a working update of
   an active user on `dev`.
2. Check whether the V3 API offers an update for the scalar fields used here.
3. Consider applying group/role changes even when the scalar update is not
   needed (no scalar field changed), so membership-only updates do not depend
   on the V2 call.
4. Add a test with `newTestClient` for the fixed request.

---

## Mitigation (2026-09-30)

`user update --interactive` now edits only user group and role assignments
and applies them through the V3 assignment endpoints, which work. New
commands `user update-roles` and `user update-groups` cover the same changes
for scripts. Scalar property updates (`user update --from-file`) remain
unsupported until a working endpoint is confirmed.

Finding: the role assignment endpoints match the role **display name**, not
`roleName` (for example `Data Integration Data Previewer`, not
`Data Preview`). `UpdateUser` sends `roleName`, so its role sync would also
fail for roles whose display name differs.
