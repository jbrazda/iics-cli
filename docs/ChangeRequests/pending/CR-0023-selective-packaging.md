
# CR to finalize support for Selective packaging

Now that we implemented comprehensive Manifest driven Package metadata andDependency checks, we can finalize the Selective package create parameter to drive Selective dependency aware deployment

See the following files

- docs/ChangeRequests/completed/CR-0021-CI-piepline-integration.md
- docs/ChangeRequests/completed/CR-0022-relase-manifest-creds.md

- we need to add support for build descriptor (csv,json,yaml,txt) as an input file to drive package selection
   - should we add support to release plan command to also output yaml and json or just keep it csv?
   - the package manifest can be passed in as stdin input or --manifest-file (short -f) parameter
   - stdin to package create should auto-detect format and apply the file list selection accordingly
   - the .txt file content should have backward compatible mode for txt files used by the official IIC CLI v2
- the package create command should include all assets listed in the package manifest if the package manifest contains path or location  pointing only to ProjectName.Project or ProjectName/FolderName.Folder it must include all assets within the folder
- Package Create Command must generate the `xexportPackage.chksum` checksum file calculated after content of the package is is determined, Only include checksums of the files actually included in the final package x
- Package must contain the ContentsofExportPackage_[package_name].csv ( the package_name name should default to filename part of the --target parameter and be possible to override using to --name  parameter). this file should contain a matching structure to export file format (objectPath,objectName,objectType,id), listing the actual file assets included in the package
- Package must contain the exportMetadata.v2.json assembled from the selected assets included in the package
- it should use exportMetadata.v2.json in the --source workspace root to lookup the corresponding asset metadata using the id, location or path  to lookup the object, whichever is available in the input or --manifest-file content
- If the package manifest contains only Folder and Project references ( no explicit assets references) it should automatically include all SYS folder assets references
- If the package manifest contains the mix of folder and direct asset reference it should  include all assets in the folder, de duplicate potential duplicates and print out warning when duplicates are found ( that would be applicable for hand coded  manifests)

## Considerations

- Should we add release-manifest as generated by the release manifest command reference? This can help minimize glue code in CI to generate packages for each environment based on the release manifest yaml or just expect CI to provide corresponding parameters for each environment package? We might need to do pre-processing for each environment to adjust some asset attributes dynamically during build to adjust environment specific settings such as logging levels or Agent group associations. Should we keep flexibility to Invoke build for each environment individually  on CI level or rely on bulk processing of all environment packages.
- It seems to be beneficial to include the Object id in the output of release plan  or objects dependencies commands that feed into the environment specific package and publish csv,json,yaml manifest files as we currently include only the Location
- Consider adding --exlude-manifest-file and --exclude regex parameter to support exclusion of assets from the package based on the manifest file content. This can be used to exclude certain assets from the package while still including the rest of the assets in the manifest file. The exclusion manifest file can have the same format as the inclusion manifest file and can be processed in a similar way to determine which assets to exclude from the final package. this would mostly useful for hand crafted manifest files to exclude certain assets without having to remove them from the manifest file. It can also be used in CI to generate a base package manifest and then use exclusion manifest to generate different environment specific packages based on the same base manifest. This can help minimize duplication of manifest content and make it easier to maintain the manifest files. We can also consider supporting exclusion based on regex patterns for more flexibility in excluding assets from the package.
- Consider adding support to write the build manifest into specified file path using --build-manifest-report parameter. which will default target/iics/import/logs/release-manifest.md and will append the content if the file already exists. This can be useful to keep track of the build history and the corresponding manifest files used for each build. It can also be used to generate reports or audit trails of the builds and the corresponding packages generated. The build manifest report can include information such as the package name, the manifest file used, the assets included in the package, and any warnings or errors encountered during the build process. This can help with troubleshooting and debugging issues with the package creation process.
- Consider adding support for generating a diff report between the package manifest and the actual content included in the package. This can help identify any discrepancies between the manifest and the actual package content, such as missing assets or unexpected assets included in the package. The diff report can be generated in a human-readable format, such as a markdown file, and can include details about the differences between the manifest and the package content. This can be useful for troubleshooting and debugging issues with the package creation process, as well as for auditing and compliance purposes to ensure that the package content matches the intended manifest specifications.

## Review findings and suggestions

1. Keep this CR focused on selective package assembly in `package create`.
2. Defer release plan JSON and YAML output to a follow-up CR to reduce scope risk.
3. Use `--manifest-file` with short flag `-m`, not `-f`, because `-f` is already
   used by `--force` in `package create`.
4. Reuse existing artifact input parsing semantics (`txt`, `csv`, `json`, `yaml`)
   and stdin format auto-detection patterns already used in export flows.
5. Keep backward compatibility by preserving current behavior when no manifest
   input is provided.

## Suggested scope for this CR

### CLI additions

- `iics package create --manifest-file <path>` for inclusion manifest input.
- Optional stdin manifest input when `--manifest-file` is not provided.
- Optional `--name` for controlling `ContentsofExportPackage_<name>.csv`.

### Selection semantics

- Accept references by `id`, `location`, or `path` and optional `type`.
- If manifest references `Project` or `Folder`, include all contained assets.
- For mixed direct and container references:
  - include union of selected assets
  - deduplicate by stable key
  - emit warnings for duplicates
- Include SYS-rooted assets implied by selected containers.

### Generated package outputs

- Regenerate `exportPackage.chksum` from final selected files only.
- Regenerate `exportMetadata.v2.json` for selected assets only.
- Generate `ContentsofExportPackage_<name>.csv` for selected assets.

## Proposed implementation plan

1. Add manifest input plumbing to `package create` (file and stdin).
2. Build metadata indexes from source `exportMetadata.v2.json` for fast lookup:
   - by id
   - by normalized location
   - by path and type
3. Implement selection resolver:
   - resolve direct references
   - expand project and folder references
   - include implied SYS assets
   - deduplicate and collect warnings
4. Filter package file set to selected assets and regenerate package metadata
   outputs (`exportMetadata.v2.json`, contents CSV, checksum).
5. Add tests for:
   - input format variants
   - folder and project expansion
   - mixed reference dedupe warnings
   - generated output integrity
6. Update docs and completions.

## Acceptance criteria

1. `package create --manifest-file` packages only selected assets.
2. Piped stdin manifests are supported with format auto-detection.
3. Folder and project manifest entries expand to contained assets.
4. Duplicates are deduplicated and reported.
5. Generated package includes selected-only metadata and checksum outputs.
6. Running `package create` without manifest input preserves existing behavior.
